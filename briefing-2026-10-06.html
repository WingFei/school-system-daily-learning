Reliable attendance starts with clear business rules.

Prevent duplicates, correct mistakes and preserve the history that school staff need.

Today’s lesson applies to a staff-operated attendance kiosk and carries over to enrolment, assessments and payments. The advice is a recommended design; news marked Confirmed is supported by linked official sources.

1. Developing a new school management system

Define business rules before building buttons

A page can look complete while leaving its important behaviour undefined. An attendance kiosk with Check In, Check Out, Delete and Clear Session buttons needs answers to these questions:

  • Can a student check in twice?
  • Can a student check out without checking in?
  • What happens when two devices submit at the same time?
  • Does “Clear Session” clear the display, end kiosk operation or remove attendance?
  • Can staff correct attendance after finalisation?

Business rules are conditions enforced regardless of which page or device sends the request.

Separate the session, device and record

ConceptMeaningExample
Teaching sessionThe scheduled lessonMathematics, 6 October, 7–9 pm
Kiosk operating contextThe lesson selected on a deviceReception tablet operating for that lesson
Attendance recordA student’s attendance for that lessonST001 checked in at 6:58 pm
Recommendation: Clearing the kiosk context should return the device to session selection. Attendance correction should be a separate, clearly labelled action.

Define permitted transitions

For a basic system with one check-in and one check-out per student per session:

Current situationActionResult
No attendanceCheck inCreate attendance
Already checked inCheck in againReturn the existing result
Checked in, no check-outCheck outRecord check-out
Already checked outCheck out againReturn the existing result
No check-inCheck outExplain that check-in is required
Incorrect recordStaff correctionRequire permission, reason and history

Returning the existing result is useful after a repeated tap or a network retry. This is idempotent behaviour: repeating an operation does not repeat its business effect. If students may leave and re-enter, use multiple visits or an event history instead of one check-in/check-out pair.

Enforce critical rules in the database

A page-level duplicate check cannot handle every simultaneous request. Two devices can both see “no attendance” before either inserts. A database uniqueness rule provides final protection.

This learning example assumes one valid attendance record per student per teaching session:

CREATE TABLE dbo.AttendanceLearning (
    AttendanceID bigint IDENTITY(1,1) NOT NULL PRIMARY KEY,
    SessionID bigint NOT NULL,
    StudentID bigint NOT NULL,
    CheckInUtc datetime2(0) NOT NULL DEFAULT SYSUTCDATETIME(),
    CheckOutUtc datetime2(0) NULL,
    IsVoided bit NOT NULL DEFAULT 0,
    RowVer rowversion,
    CONSTRAINT CK_AttendanceLearning_Time
        CHECK (CheckOutUtc IS NULL OR CheckOutUtc >= CheckInUtc)
);
CREATE UNIQUE INDEX UX_AttendanceLearning_Valid
ON dbo.AttendanceLearning (SessionID, StudentID)
WHERE IsVoided = 0;

The filtered unique index prevents two non-voided records for the same student and session. SQL Server supports filters on unique indexes. Microsoft documentation.

Catch the duplicate-key error, retrieve existing attendance and display a helpful result. Production design also needs student/session foreign keys, correction reasons, staff identities and audit history.

Prevent staff from overwriting each other

If two staff members open the same record, a later save can overwrite an earlier correction. Include the original row version in the update:

UPDATE dbo.AttendanceLearning
SET CheckOutUtc = @CheckOutUtc
WHERE AttendanceID = @AttendanceID
  AND RowVer = @OriginalRowVer
  AND IsVoided = 0;

If zero rows are affected, reload and explain that the record changed or is unavailable. SQL Server’s rowversion changes on updates; it is a binary version marker, not a date or time. Official documentation updated 20 July 2026.

Recommendation: Save a correction and its audit entry in one database transaction so both succeed or both fail.

2. New ideas for system improvement

A. Audited attendance correction

NOW · MEDIUM EFFORT

Problem: Staff need to remove mistaken check-ins, but deletion makes discrepancies harder to explain.

Workflow: Staff select “Void attendance”; the server checks correction permission; staff provide a reason; the record is marked voided; the system records who acted, when and what changed. Normal reports exclude the voided record while authorised history views retain it.

For a bulk correction, show the teaching session and affected count before submission. A batch reference should connect the changes.

Measure: Attendance disputes, investigation time and the percentage of corrections with complete reasons.

Data: Attendance ID, acting staff ID, reason, time, previous values and batch reference.

Edge cases: Exported attendance, finalised lessons, wrong session selection and reports that include voided records. Downstream exports may need a correction process.

First release: Individual voiding with history, followed by bulk correction once the rules are proven.

B. Staff exception dashboard

NEXT · MEDIUM FOR ATTENDANCE ONLY

Problem: Incomplete records are discovered through manual reports or student complaints.

Workflow: Show an actionable list on staff login: missing check-out after a lesson, attendance awaiting finalisation, applications awaiting documents, and payments awaiting reconciliation. Link each item to its record.

Measure: Unresolved exceptions, resolution time and manual follow-ups.

Data: Session end time, attendance status, document checklist, payment status and responsible centre/staff.

Edge cases: Approved absences, overnight lessons, cancellations, payment delays and repeated alerts.

Scope: Medium for attendance only; Large across multiple modules. Start with missing check-out and measure its usefulness. A scheduled SQL query is sufficient initially.

4. Current trends in system behaviour

Explain what happened and what happens next

This is a recommended modern design pattern, rather than a measured claim about Singapore schools. A spinner alone does not tell a student whether attendance was saved.

Check-inPage refreshes“Checked in at 7:02 pm” after saving
Repeated tapGeneric error“You already checked in at 7:02 pm”
Response lost“Failed”“Unable to confirm. Checking your attendance status…”
Kiosk context cleared“Cleared”“Kiosk session ended. Select the next lesson.”
Concurrent staff editLast save overwrites“This record changed. Reload before correcting it.”

Students gain confidence; staff handle fewer repeated submissions; parents can understand whether application and payment actions are saved, pending review or require attention.

Trade-off: More states require more implementation and verification. A clear server response may be sufficient without real-time technology.

Small improvement: Include the saved action, teaching session and time in attendance feedback. Keep it visible long enough to read, then return a shared kiosk to its ready screen. Display success only after the server confirms the database operation.

5. Today’s practical exercise

Prove duplicate prevention · 25 minutes

Use a development database.

  1. 5 minutes: Run the learning table and index script.
  2. 3 minutes: Insert attendance using the statement below.
  3. 3 minutes: Repeat the insert. Confirm that the duplicate is rejected.
  4. 4 minutes: Void the original row using the update below.
  5. 3 minutes: Repeat the insert. Confirm that a replacement succeeds.
  6. 3 minutes: Inspect the rows using the select below.
  7. 4 minutes: Write the message your VB.NET page should show after catching a duplicate-key error. Retrieve existing attendance and explain the result.
-- Insert, then repeat to verify duplicate rejection
INSERT dbo.AttendanceLearning (SessionID, StudentID)
VALUES (1001, 2001);

-- Void the original, then run the insert again
UPDATE dbo.AttendanceLearning
SET IsVoided = 1
WHERE SessionID = 1001 AND StudentID = 2001 AND IsVoided = 0;

-- Inspect the two historical rows
SELECT AttendanceID, SessionID, StudentID,
       CheckInUtc, IsVoided, RowVer
FROM dbo.AttendanceLearning
WHERE SessionID = 1001 AND StudentID = 2001;

Verification: Two historical rows, exactly one non-voided row, and no extra row from the rejected duplicate attempt.

Key takeaway: Reliable school workflows need database rules, clear state changes and traceable corrections.

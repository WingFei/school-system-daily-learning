Test the school workflow, not only the page.

Turn permissions, record states and concurrency rules into repeatable evidence before a release.

Yesterday’s lesson defined who may act on which records. Today we convert those decisions into tests. The same method applies to attendance corrections, admissions approval, enrolment changes, assessment publishing, fee adjustments, payments and portal access.

1. Developing a new school management system

Today’s lesson: test business outcomes at three levels

A button that works during one developer test does not prove the workflow is safe. A school operation can fail because the wrong staff member is allowed, the record changed after it was loaded, a database transaction partly completed, or the browser repeated a request.

Start with an exact business statement: an attendance supervisor may correct an open attendance record for an assigned centre after recent identity verification; the correction and audit entry must either both save or both fail. That one sentence supplies most of the important test cases.

Test levelQuestion answeredAttendance exampleSpeed and scope
Business-rule/unit testDoes one decision behave correctly?Supervisor A is denied a Centre B recordFast; no browser or real database
Integration testDo the service, security and database work together?Correction and audit row commit in one transactionSlower; focused important paths
End-to-end testCan a real user complete the critical journey?Sign in, verify, correct and see confirmationSlowest; a small critical set

Use many focused rule tests, fewer integration tests and a small set of end-to-end journeys. This is not a rigid percentage. A fee posting or result publication deserves deeper coverage than changing a dashboard preference.

Build a test matrix before writing test code

A matrix prevents the “happy path only” habit. Change one condition at a time and state the expected result.

CasePermissionScopeRecord stateVerificationExpected result
1CorrectCentre AOpenRecentSave correction and audit
2View onlyCentre AOpenRecentDeny; no data change
3CorrectCentre B onlyOpen Centre A recordRecentDeny without exposing student details

7CorrectCentre AOpenRecentRepeated request has one business effect

Also test account suspension after the page opens, malformed identifiers, missing records, invalid correction reasons and failure while writing the audit row. A test is strongest when it checks both the response and the absence of unintended changes.

Small C# example: express the rule as a test

This example uses fictional types and xUnit-style assertions to show the pattern. It is not a complete production implementation.

[Fact]
public async Task CorrectAttendance_WrongCentre_DoesNotChangeRecord()
{
    // Arrange
    var staff = TestStaff.Supervisor(centreId: 20);
    var record = TestAttendance.Open(centreId: 10);
    var originalTime = record.CheckInUtc;

    // Act
    var result = await service.CorrectAsync(
        staff, record.Id, record.RowVersion, "Wrong lesson");

    // Assert
    Assert.Equal(CorrectionStatus.Forbidden, result.Status);

    var saved = await repository.GetAsync(record.Id);
    Assert.Equal(originalTime, saved.CheckInUtc);
    Assert.Empty(await audit.FindForAsync(record.Id));
}

The final two assertions matter. A forbidden response is insufficient if the code changed the record before deciding to deny the request.

Test concurrency deliberately

Open the same record twice using the same original rowversion. Save Staff A’s correction, then submit Staff B’s stale copy. The first should succeed; the second should affect zero rows or raise the controlled concurrency result. Verify that Staff A’s values remain and that only the successful change receives an audit entry.

For repeated submissions, use a stable request identifier or enforce the relevant uniqueness rule. Send the same correction twice and verify that the second request returns the existing outcome instead of creating another correction or notification.

Use a database that can reveal real behaviour

Confirmed: Microsoft’s EF Core testing guidance recommends good coverage against the actual production database system. It warns that SQLite or in-memory substitutes can differ in query behaviour, transactions and provider-specific features. Official EF Core guidance, updated 30 January 2023.

For your current system, run important SQL Server tests against a disposable SQL Server test database, never production. For a future application, test important EF Core queries against the chosen production database engine as well. If you later choose MariaDB, a test passing against SQL Server or an in-memory provider does not prove MariaDB SQL translation, collation or transaction behaviour.

AreaExisting VB.NET Web Forms + SQL ServerNew ASP.NET Core + React
Starting pointExtract one rule from code-behind into a VB service classKeep rules in application services behind API endpoints
Rule testsAdd a Visual Basic test project around extracted servicesAdd C# unit tests around services and authorisation handlers
Database testsUse a resettable SQL Server test database and transaction-aware fixturesUse integration tests with the selected EF Core provider and isolated data
Page/API testsVerify postback/callback handlers call the protected serviceUse a test web host for API responses and authentication states
Browser testsKeep a short smoke pack for critical Web Forms journeysAutomate only critical React journeys; keep business rules below the UI

Legacy recommendation: Do not wait for a complete rewrite. Pick the riskiest existing handler, extract its decision logic, and add characterisation tests that capture today’s correct behaviour before changing it.

New-system recommendation: Make testability part of the architecture. Pass identity, clock and request identifiers through interfaces so tests can control them. Keep React responsible for interaction; the API remains the final authority.

Define “ready to release” with evidence

  • All permission, centre-scope and record-state cases pass.
  • A failed correction leaves attendance and audit data unchanged.
  • A stale edit preserves the newer record.
  • A repeated request creates one business effect.
  • Reports and exports reflect the corrected status.
  • Logs identify the request without storing secrets or unnecessary student data.

A green test suite does not eliminate review, security assessment or user acceptance testing. It gives the team repeatable evidence that known rules continue to work.

2. New ideas for system improvement

A. Critical-workflow regression pack

NOW · MEDIUM EFFORT

Problem and users: Developers retest screens manually after fixes, while school staff discover regressions in attendance, enrolment or payments. Manual checks vary between releases.

Workflow: Select five high-risk journeys. For each, keep a short rule matrix, automated service/integration tests and one release checklist. Run fast tests on every change and database/browser tests before deployment. A failed critical test blocks release until reviewed.

Benefits and measures: Fewer escaped defects and faster, consistent release checks. Measure critical tests automated, pass rate, release verification time and production incidents linked to covered journeys.

Data/integrations: Fictional students, staff roles, centre assignments, test sessions, a resettable database and build pipeline integration. Payment tests should use the provider’s sandbox or a controlled stub, never live cards.

Edge cases: Order-dependent tests, shared data, timezone boundaries, flaky browser timing, unavailable external sandboxes and schema migrations. Tag slow tests separately and keep test data deterministic.

First slice: Attendance correction, duplicate check-in, stale update, unauthorised centre and transaction rollback.

B. Reusable school test-data scenarios

NEXT · SMALL TO START

Problem and users: Developers create ad hoc records that miss realistic relationships. Test databases may contain copied personal data, creating privacy and repeatability risks.

Workflow: A script creates named fictional scenarios: “active student with parent”, “withdrawn student”, “unpaid invoice”, “finalised assessment” and “cross-centre staff”. Each scenario has stable identifiers and an expected state. The test run resets only its assigned dataset.

Benefits and measures: Faster defect reproduction and safer demonstrations. Measure setup time, tests using approved scenarios, copied-production-data findings and failures caused by missing relationships.

Data/integrations: Synthetic names and contacts, referentially valid programme/intake/enrolment/fee data, scenario version and cleanup process. No external integration is required for the first release.

Edge cases: Unique email/ID constraints, date-sensitive intakes, parallel test runs, reports with large datasets and accidental outbound email/SMS. Route all test notifications to a sink and mark the environment visibly.

First slice: One fictional student, two centres, three staff permission profiles and an attendance session with open/finalised variants.

3. News and development tools

Previously covered .NET, NuGet, DevExpress and React items are not repeated. Two useful official testing resources are highlighted instead; documentation update dates are not software release dates.

ASP.NET Core integration testing with WebApplicationFactory

Official Microsoft guidance, updated 24 September 2026 · checked 8 October 2026.

Confirmed: ASP.NET Core supports integration tests with a test web host and in-memory test server. The Microsoft.AspNetCore.Mvc.Testing package provides WebApplicationFactory. Microsoft recommends separating unit and integration test projects and limiting broader integration tests to important infrastructure scenarios.

School relevance/use case: Send a correction request through the real request pipeline and verify authentication, authorisation, validation and response handling together.

Compatibility/licensing/cost: Check package versions against the exact target framework. This guidance does not verify compatibility with DevExpress 23.1, React libraries or your hosting environment. The Microsoft documentation does not state a separate commercial licence fee for this package; infrastructure and engineering effort still have costs.

Recommendation: Adopt for the new ASP.NET Core system. Begin with one protected endpoint and a separate test database. Continue using service-level tests for most rule combinations.

dotnet test for repeatable command-line checks

Official Microsoft guidance, updated 12 September 2026 · checked 8 October 2026.

Confirmed: dotnet test builds test projects and runs their configured test framework. The current guidance also shows ways to route framework-specific command-line arguments when a solution contains different test frameworks.

School relevance/use case: Run permission and fee-calculation tests consistently on a developer machine and later in a build pipeline.

Compatibility/licensing/cost: Use test SDK/framework versions compatible with the target .NET version. Test framework packages and CI services have their own licences or usage terms; no CI pricing is inferred here. This command does not test a legacy .NET Framework Web Forms application unless its test project and runner support that setup.

Recommendation: Adopt. Add one documented command for fast tests and a separate command or filter for integration tests so developers know what must pass before committing and releasing.

4. Current trends in system behaviour

Drafts that save safely and can be resumed

This is a recommended modern interaction pattern, not a measured claim about all Singapore schools. Long admissions and course-enrolment forms should tolerate interruption without confusing a draft with a submitted application.

SituationTraditional behaviourImproved behaviour
Applicant leaves midwayEntered data is lostVerified account sees a clearly labelled draft
Network drops during saveSpinner or generic failure“Not yet saved”; retry without duplicate records
Applicant returnsStarts a new formResumes the most relevant active draft
Application submittedForm still appears editableSubmitted snapshot, timestamp and next step are shown
Draft becomes outdatedOld intake remains selectableExplain changed intake rules and request review

Staff relevance: Fewer duplicate applications and support calls. Student/parent relevance: Less repeated typing and clear confidence about submission status.

Trade-offs: Draft ownership, expiry, version conflicts, consent, attachment cleanup and notification rules add complexity. Autosave must not silently mark an application as submitted.

When unnecessary: A one-question enquiry form may need only a normal submit confirmation. Autosave adds little value when completion takes seconds.

One small implementation: Add explicit Draft and Submitted states to one application flow. Display “Saved at 9:42 pm” only after server confirmation, and test that two tabs cannot overwrite newer answers silently.

5. Today’s practical exercise

Convert one attendance rule into a repeatable test · 25 minutes

Use a development project and fictional data. Do not point the exercise at production.

  1. 5 minutes: Choose the rule “staff cannot correct attendance outside their assigned centre.” Write its allowed and denied cases in plain English.
  2. 5 minutes: Locate the current server-side decision. If it sits in code-behind, extract the decision into a small function or service that accepts staff permissions, assigned centre and record centre.
  3. 7 minutes: Add two tests: Supervisor A + Centre A returns allowed; Supervisor A + Centre B returns denied.
  4. 4 minutes: In the denied test, also verify that attendance values and audit rows are unchanged.
  5. 2 minutes: Run the test twice. Change the implementation deliberately so the wrong-centre case passes, confirm the test fails, then restore the rule.
  6. 2 minutes: Record the command or Visual Studio action used to run it so another developer can reproduce the result.

Verification: Both tests pass with the correct implementation, the deliberate defect is detected, and the denied case proves no data-changing method was called. If extracting the rule safely takes longer, complete the matrix and function boundary today; do not rush a production edit.

Today’s key takeaway: A reliable school system proves both that permitted actions work and that denied, stale or repeated actions leave data safe.

Recommended next action: Add the wrong-centre attendance test and make it part of your normal pre-release check.

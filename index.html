1. Developing a new school management system

Today’s lesson: separate modules without starting with microservices

A modular monolith is one deployable application whose internal modules have explicit responsibilities. Admissions, enrolment and finance may run in the same process and database initially, but they do not treat every table and class as shared property.

This is a good Phase 1 default for a small development team: deployment, debugging and transactions remain manageable. You still prepare for future growth by separating business rules from the UI and assigning each important record to one module.

Do not split the first release into many network services merely because the system has many menu items. A microservice adds independent deployment, monitoring, network failure, versioning and data-consistency work. Split a module later only when there is a concrete reason such as independent scaling, a separate team, a different availability requirement or a stable integration boundary.

This list is a starting map, not ten separate applications. Phase 1 can begin with Identity & Access, People, Academic Structure, Admissions and Enrolment. Add Attendance and Finance when their end-to-end workflows are ready.

Give each record one owner

Ownership answers: “Which module is allowed to create and change this record?” Admissions owns an application. People owns the person profile. Enrolment owns the student’s relationship to an intake. Finance owns the invoice.

When an application is accepted, Admissions should not directly update every enrolment and finance table. It submits a defined command or publishes an internal event. Enrolment creates the enrolment using its own rules; Finance creates charges only when the fee policy requires them.

HandoffRecommended contractAvoid
Admissions → PeopleCreate or match person using verified identity/contact dataAdmissions writing directly into profile tables
Admissions → EnrolmentAccept offer with application, person, intake and effective dateDuplicating enrolment rules in the offer page
Enrolment → FinanceRequest initial charge with enrolment and fee-plan referencesA database trigger that hides business decisions
Attendance → ReportingExpose finalised attendance summaryReports interpreting raw correction history differently

Within the first monolith, these contracts can be C# interfaces and application commands. They do not have to be HTTP calls or a message broker. The boundary is conceptual and enforced by project references, namespaces, reviews and tests.

Practical Phase 1 solution structure

SchoolSystem.sln
├─ src/
│  ├─ SchoolSystem.Web
│  │  └─ Blazor pages/components, DevExpress UI, authentication shell
│  ├─ SchoolSystem.Application
│  │  └─ Use cases, commands, queries, validation, permissions
│  ├─ SchoolSystem.Domain
│  │  └─ Business entities, value objects and rules
│  └─ SchoolSystem.Infrastructure
│     └─ EF Core, MariaDB provider, files, email and external adapters
└─ tests/
   ├─ SchoolSystem.UnitTests
   └─ SchoolSystem.IntegrationTests

Start with these four production projects rather than one project per module. Organise each project by module folders such as Admissions, People and Enrolment. If a module becomes large and stable enough, it can move to separate projects later.

Allowed reference direction: Web → Application; Infrastructure → Application/Domain; Application → Domain. Domain should not reference Web, DevExpress, EF Core or MariaDB packages. This keeps core rules testable and prevents a UI control or database provider from becoming the business model.

Confirmed: Microsoft’s architecture guidance recommends keeping presentation responsibility in the UI, data access in infrastructure and business logic in the application core. Official architectural principles, updated 9 May 2023.

A small command boundary

The UI sends intent to the application layer. It should not assemble database rows itself.

public sealed record AcceptOfferCommand(
    Guid ApplicationId,
    Guid IntakeId,
    DateOnly EffectiveDate,
    byte[] OriginalVersion);

public interface IAdmissionsService
{
    Task<AcceptOfferResult> AcceptOfferAsync(
        AcceptOfferCommand command,
        CurrentStaff staff,
        CancellationToken cancellationToken);
}

The service loads the application, checks permission and current state, performs matching/creation through defined module interfaces, and records the audit result. A Blazor component or React page displays the outcome. DevExpress components handle presentation and interaction; they do not decide whether an offer may be accepted.

Blazor Interactive Server affects deployment, not module ownership

Confirmed: Microsoft documents Interactive Server as interactive server-side rendering using a real-time browser connection. Blazor Web Apps can use static server rendering, Interactive Server, Interactive WebAssembly or Interactive Auto. Official render-mode guidance, updated 26 August 2026.

For your internal staff system, Interactive Server can reduce front-end duplication because C# runs on the server. Plan for connection loss, reconnection messages, server capacity and load-balanced deployment if you scale out. Keep draft application data in the database rather than only in a user’s live circuit.

For a public applicant portal, evaluate network conditions and hosting scale before choosing a render mode. React remains a valid client option if your team prefers an API-first UI. In either case, the application and domain layers should own the rules.

Database/provider compatibility is an architectural decision

EF Core is not the MariaDB provider itself. Verify the exact combination of .NET, EF Core, provider and MariaDB Server before fixing the baseline.

Confirmed: the latest published Pomelo EF Core MySQL provider release visible on 9 October 2026 is 9.0.0, published 17 August 2025. Its release notes state compatibility with EF Core 9.0.x and testing against MariaDB through 11.6 among the listed versions. They do not claim EF Core 10 or MariaDB 13 compatibility.

Recommendation: Before creating the production solution, make a one-page version matrix covering .NET, EF Core, database provider, MariaDB Server and DevExpress Blazor. Choose only a combination explicitly supported by every critical dependency. “Newest” is not automatically the safest baseline.

2. New ideas for system improvement

A. Intake readiness checklist

NOW · MEDIUM EFFORT

Problem and users: Admissions staff open an intake before fees, documents, schedules or application rules are complete. Applicants then encounter missing options and staff perform manual corrections.

Workflow: Before an intake becomes “Open for Application”, the system checks named prerequisites: active course/intake dates, application form, required-document set, fee plan, capacity policy, offer template and responsible staff. The owner sees Passed, Warning or Blocking items and resolves them before activation.

Benefits and measures: Fewer incomplete intakes and post-opening fixes. Measure blocked activation issues found, applicant errors, staff correction time and intakes opened with unresolved warnings.

Data/integrations: Academic structure, admissions configuration, finance fee plans, document rules and template status. No external integration is required initially.

Edge cases: Rolling admissions, optional documents, centre-specific fees, late changes and emergency reopening. Version the checklist result and re-evaluate it when a dependency changes.

Module lesson: Admissions owns the activation decision but queries readiness from Academic Structure, Finance and Communications through explicit interfaces.

B. Student activity timeline as a read model

NEXT · MEDIUM EFFORT

Problem and users: Staff move across application, enrolment, attendance, finance and communication screens to understand what happened. This increases support time and encourages broad database access.

Workflow: Each module emits a safe summary event—application submitted, offer accepted, enrolment activated, payment received, attendance corrected. A timeline projection stores only authorised display data. Staff see a chronological view with links to records they are permitted to open.

Benefits and measures: Faster investigation and fewer cross-module searches. Measure average case-handling time, screens visited per enquiry and timeline events without a resolvable source.

Data/integrations: Event type, occurred time, actor, student/person reference, centre, source record and display-safe summary. Begin with internal database events; a message broker is unnecessary for Phase 1.

Edge cases: Corrected or voided events, privacy-sensitive notes, duplicate delivery, out-of-order events, retention and permission changes. The timeline is a read model, not a second place to edit business records.

Module lesson: Reporting owns the projection; source modules remain the authority.

Visual Studio 2026 September update

Published 29 September 2026 · Official Microsoft announcement.

Confirmed: The stable-channel update added preview Bring Your Own Model support, a Copilot action for NuGet Audit warnings, Git pull-request assistance, clearer highlighting of the deciding operand in C# compound conditions and Podman container attachment. MariaDB Server 13.0.2 becomes Stable

Stable on 17 September 2026 · Official MariaDB Foundation newsletter.

Confirmed: MariaDB describes 13.0.2 as Stable but a rolling release, not LTS, and points to 11.8 LTS when a longer maintenance window is the priority.

School relevance/use case: Your database baseline will hold long-lived admissions, fee and assessment records, so support duration and provider compatibility matter more than adopting the newest feature set.

4. Current trends in system behaviour

Permission-aware global search and quick actions

This is a recommended interaction pattern, not a measured claim about all schools. Staff increasingly work from a task or person rather than remembering which module contains the right page.

SituationTraditional behaviourImproved behaviour
Reception receives a callChoose module, screen and search fieldSearch name, student ID, application or receipt from one entry point
Several matches existOpen records one by oneShow type, centre, status and safe distinguishing details
Staff lacks permissionRecord appears, then access failsUnauthorised records are omitted or safely represented
Record is foundReturn to menus for next stepOffer permitted actions such as View profile or Open application
No match existsBlank gridExplain search tips and permitted next steps

Staff relevance: faster reception and support work. Student/parent relevance: faster answers and fewer repeated details, although public portals should normally search only the signed-in user’s own records.

Trade-offs: Search indexes, ranking, privacy, typo handling and permissions add complexity. Logging full search text may capture NRIC, phone numbers or other personal data; minimise and protect logs.

When unnecessary: A small module with one short list may be clearer with a normal filter. Do not replace predictable navigation entirely.

One small implementation: Build an internal quick search for Student ID and exact application reference first. Return a maximum result count, include record type and centre, enforce permissions in the server query and show a useful no-result state. Add fuzzy name search only after privacy and ranking rules are agreed.

5. Today’s practical exercise

Create a Phase 1 ownership map · 25 minutes

Use a document or spreadsheet; no production code is required.

  1. 5 minutes: List five Phase 1 modules: Identity & Access, People, Academic Structure, Admissions and Enrolment.
  2. 5 minutes: Assign each key record to exactly one owner: StaffAccount, Person, Course, Intake, Application, Offer and Enrolment.
  3. 5 minutes: Write one command for each cross-module handoff, such as AcceptOffer or CreateEnrolmentFromOffer. Describe required inputs without copying entire database rows.
  4. 5 minutes: Mark every existing or proposed direct table write that crosses an ownership boundary. Replace one with a service/interface call in the design.
  5. 5 minutes: Check the solution structure above against your chosen stack. Write the exact .NET, EF Core, MariaDB provider, MariaDB Server and DevExpress versions that still require verification.

Verification: Every key record has one owner, every handoff has a named contract, no UI component owns business rules, and the version matrix contains no unverified compatibility assumption marked as approved.

Today’s key takeaway: Start with one deployable application, but make module ownership and dependency direction explicit from the first day.

Recommended next action: Approve the five-module Phase 1 map and verify one complete technology version combination before creating the production solution.

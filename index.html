Give staff the right access to the right records.

Design permissions around actions, centres and recent identity verification.

Yesterday we defined reliable attendance behaviour. Today we decide who may perform each action. The same approach protects admissions decisions, assessment changes, fee adjustments and student exports across Singapore schools, tuition centres, private education institutions and training providers.

1. Developing a new school management system

Today’s lesson: authorise the action and the individual record

Authentication establishes who signed in. Authorisation decides what that person may do. A receptionist might have a valid staff account and still lack permission to change published results. A centre manager might be permitted to correct attendance at Centre A but have no access to Centre B.

Therefore, “staff logged in” is only the beginning of a decision. Ask: is this account active, is this action permitted, does the record belong to an allowed school or centre, and is the record in a state where the action is valid?

A realistic correction workflow

Mei manages Centre A. She notices that a student was marked present at the wrong lesson. The server loads the attendance record using its identifier and determines its actual institution, centre and session. It checks Mei’s attendance-correction permission and centre assignment. It checks whether the lesson is finalised. If the correction requires additional verification, Mei verifies her own identity, reviews the selected record and enters a reason. Immediately before saving, the server checks the current permission and record state again.

Why check again? A browser can stay open after staff access changes. The lesson may also be finalised while a confirmation dialog is open. A permission decision made earlier should not silently authorise a later operation against changed conditions.

Use three building blocks

  • Role: a convenient collection of permissions, such as Reception or Finance Officer.
  • Permission: a specific action, such as Attendance.Correct or Fees.Adjust.
  • Scope: the records where the action is allowed, such as Centre A or assigned classes.

Store these separately enough that a transferred employee can keep a role while changing centre assignments. Start with a few explicit permissions rather than creating a different role for every combination. Default to denying an action when no matching grant exists.

For a multi-school product, institution scope must also be enforced. Centre identifiers alone may be insufficient. Student and parent portals need ownership checks: a student sees their own record, while a parent sees records allowed by a current, verified relationship. A record ID supplied by the browser is a lookup key, not evidence of ownership.

Small VB.NET example: keep the decision on the server

The following is service-level pseudocode, showing order rather than a complete production handler. The named services are components you implement; they are not built-in DevExpress APIs.

' Illustrative VB.NET service flow
Dim staff = IdentityService.GetCurrentStaff()
Dim record = AttendanceRepository.GetById(attendanceId)

If record Is Nothing Then Throw New InvalidOperationException("Unavailable")
If Not AccessService.CanPerform(staff, "Attendance.Correct",
                               record.InstitutionId, record.CentreId) Then
    Throw New UnauthorizedAccessException("Access denied")
End If
If record.IsFinalised Then
    Throw New InvalidOperationException("Reopening approval required")
End If
If Not VerificationService.IsRecentFor(staff, "Attendance.Correct") Then
    Throw New UnauthorizedAccessException("Verify identity to continue")
End If

' Service rechecks state and saves correction + audit atomically.
AttendanceService.Correct(staff, record.Id, originalRowVersion, reason)

Get staff identity from the authenticated server session, not a hidden field. Get centre and institution from the stored record. In a real page, translate exceptions into controlled feedback, use parameterised database commands, validate the reason and protect state-changing requests against cross-site request forgery. Callbacks, exports and direct URLs need the same access rules as normal postbacks.

Confirmed: ASP.NET Core supports resource-aware checks through IAuthorizationService.AuthorizeAsync. An [Authorize] attribute alone cannot make a decision that depends on a record loaded later. Microsoft resource-based authorisation guidance, updated 22 July 2026.

What an extra PIN does—and does not establish

Your kiosk requirement for another PIN can create a useful pause before session management. My recommendation is individual staff verification instead of a shared centre PIN. A shared code does not identify the person approving an action. A password followed by a PIN is also not automatically multi-factor authentication: both may be knowledge-based secrets.

For a sensitive action, consider fresh sign-in or an identity-provider verification flow. If an individual PIN is retained, use a password-hashing mechanism, rate-limit attempts, expire verification and record the verified identity without logging the secret. Never store a plaintext PIN in JavaScript or send it back to the browser.

For the prototype, a five-minute verification window is a suggested policy to evaluate, not a standard. Bind the result to the current staff session and permitted operation. A change of staff, sign-out or session expiry must clear it. For bulk actions, also bind the confirmation to the selected centre, record set and affected count so a previous confirmation cannot authorise a different batch.

Make the decision explainable

For a successful correction, retain actor, action, target record, institution/centre, UTC time, reason and correlation identifier. The correlation identifier connects a request to its processing history. Record useful denied-action events without copying full student details or secrets into logs. Give audit access its own permission.

For a centre manager, “Attendance correction permission required” is useful. For an unrelated user requesting another school’s record, an unavailable-record response can avoid disclosing that the record exists. Decide this consistently; do not accidentally reveal names in error messages.

2. New ideas for system improvement

A. Time-limited staff cover assignments

NEXT · MEDIUM EFFORT

Problem and users: Relief teachers and reception staff cover another centre. Permanent access grants accumulate because managers forget to remove them.

Workflow: A manager selects staff, centre or classes, allowed actions, start time and expiry. The system activates cover access only during that interval. The manager sees an expiry list; the service evaluates validity on every request. Cover attendance access does not automatically grant fee adjustment or student export.

Benefits and measures: Reduce manual access-removal work and stale grants. Track expired grants still usable (target zero), time to arrange cover, and the number of temporary assignments without an end time.

Data/integrations: Staff identity, approved scope, permission set, effective interval, approver and reason; an existing identity provider if available. A scheduled job can send expiry notices, while server checks enforce expiry even if that job fails.

Edge cases: Overnight cover, cancelled lessons, extension requests, overlapping grants, disabled accounts and cached permissions. Store effective times consistently and display Singapore time clearly. Explicit denial or account suspension should still block a temporary grant.

First slice: One-centre attendance cover with a compulsory expiry and a manager review screen. Broader academic and finance delegation can follow after real use proves the design.

B. Permission preview for managers

NOW · SMALL FOR ONE MODULE; MEDIUM ACROSS MODULES

Problem and users: Managers and support staff struggle to understand why one employee can correct a record while another cannot. They may grant excessive access just to remove an error.

Workflow: An authorised manager selects a staff member and a fictional or appropriately scoped record, then asks “Can this person correct attendance here?” The system shows the effective grant, centre match, expiry and any remaining verification requirement. It explains the decision without signing in as that person.

Benefits and measures: Fewer access-support tickets and faster resolution. Measure time to explain a denial, unnecessary broad grants removed, and agreement between preview decisions and actual server decisions.

Data/integrations: Existing roles, permissions, scope assignments and verification policy; no external integration required. Reuse the same decision service, with an explanation result alongside allow/deny.

Edge cases: Sensitive staff information, outdated previews, time-dependent grants and permission to inspect other users. A preview must not execute the underlying action or reveal student data outside the manager’s scope.

First slice: Show “Allowed centre”, “Required permission” and “Additional verification required” for attendance correction. Include evaluated time so staff understand that access may change later.

4. Current trends in system behaviour

Ask for extra verification at the moment it is useful

This is a recommended modern interaction pattern, not a measured adoption claim about Singapore schools. Keep ordinary permitted tasks smooth, and explain additional checks when a more sensitive action is requested.

WorkflowTraditional behaviourImproved behaviour
Staff review attendanceRepeated PIN prompts for every screenNormal permitted viewing after sign-in
Staff correct a recordGeneric PIN box without contextShow record and reason; request verification when policy requires it
Staff change centrePrevious confirmation carries acrossRe-evaluate scope and action before saving
Parent requests contact changeImmediate change to a sensitive destinationExplain verification and show confirmed outcome

Staff relevance: Fewer interruptions during routine reception work and clear accountability for corrections. Student relevance: Routine attendance capture stays quick. Parent relevance: Sensitive portal changes get an understandable verification step, while ordinary viewing remains straightforward.

Trade-offs: More identity states, recovery paths and expired-confirmation cases to handle. Staff need a recovery route if their verification method is unavailable. Avoid turning a failed verification into an invitation to share a colleague’s credentials.

When unnecessary: Opening a timetable or filtering an already authorised list generally does not need another prompt. The school should decide which actions justify extra friction.

One small implementation: Add a clear action summary before attendance correction, then have the server report whether recent verification is required. Keep the summary visible after verification and recheck the selected record when saving.

5. Today’s practical exercise

Build a permission decision table · 25 minutes

Use a development copy with fictional records. The goal is to prove access decisions before connecting a destructive action.

  1. 5 minutes: Create three fictional identities: Reception A, Supervisor A and Supervisor B. Define attendance-view and attendance-correct grants for their assigned centres.
  2. 5 minutes: Write one shared function that takes authenticated staff, requested action and a loaded record. Return allow/deny plus a brief reason. Add finalised-state and recent-verification checks.
  3. 7 minutes: Evaluate the cases below in a debug page or test harness. The page must call the shared server function.
  4. 5 minutes: Change the requested record from Centre A to Centre B, expire verification and disable the account. Confirm decisions change immediately.
  5. 3 minutes: Record which rules belong to identity, permission, scope and business state. Identify one production handler that currently lacks the shared check.
CaseExpected result
Reception A views Centre A attendanceAllow if view grant exists
Reception A requests correction directlyDeny even if a button is manually shown
Supervisor A corrects open Centre A record, freshly verifiedAllow
Supervisor A targets Centre B recordDeny

Verification: All seven outcomes match, the wrong-centre and disabled-account cases never reach mutation code, and verification alone never grants missing permissions. In a real handler, confirm denied requests leave the record unchanged. Keep any diagnostic page restricted to development.

Today’s key takeaway: A valid login must be followed by server checks for the action, record scope, current state and any required verification.
